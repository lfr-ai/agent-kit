# Expand and contract (zero-downtime schema change)

During a rolling deploy, old and new application versions run against the same
database at the same time. A schema change is safe only when every running
version can work with the schema at every moment. Expand/contract splits a
breaking change into steps that are each backward compatible.

## The phases

| Phase | Database change | Application change | Rollback available |
| --- | --- | --- | --- |
| 1. Expand | Add new nullable column, table, or index | None yet | Yes: drop the new object |
| 2. Dual write | None | Write old and new shape; read old | Yes: redeploy previous app |
| 3. Backfill | Batched copy of existing rows into the new shape | None | Yes: new data is redundant |
| 4. Switch reads | Optionally add constraints (`NOT VALID`, then validate) | Read new shape, still write both | Yes: redeploy phase 2 app |
| 5. Stop old writes | None | Write only the new shape | Limited: old shape goes stale |
| 6. Contract | Drop old column, table, or index | None | No: data is gone; restore from backup |

Each phase is a separate deploy. Wait for the previous version to drain fully
(no old pods, no old workers, no queued jobs built by the old version) before
starting the next.

## Worked example: rename `orders.note` to `orders.customer_note`

1. Migration A adds `customer_note TEXT NULL`.
2. Release 1 writes both `note` and `customer_note`; reads `note`.
3. A batched data migration copies `note` into `customer_note` where it is null.
4. Release 2 reads `customer_note`, still writes both.
5. Release 3 writes only `customer_note`.
6. Migration B drops `note`, waived with `# migration-safety: reviewed` and a
   reason, after release 3 is the oldest running version.

A single `alter_column(new_column_name=...)` would break every release-0
instance the moment it ran.

## Common changes mapped to safe sequences

| Desired change | Safe sequence |
| --- | --- |
| Add a required column | Add nullable (or with a constant `server_default`) → backfill → add `CHECK (col IS NOT NULL) NOT VALID` → validate → `SET NOT NULL` → drop the check |
| Change a column type | Add a new column of the new type → dual write → backfill → switch reads → drop old |
| Split a table | Create new table → dual write → backfill → switch reads → stop old writes → drop old columns |
| Add a foreign key | Add with `NOT VALID` → validate in a later migration |
| Add a unique constraint | Create a unique index concurrently → attach it as a constraint using the index |
| Drop a column | Stop reading → stop writing → deploy → drop |
| Remove an enum value | Stop writing the value → migrate rows → recreate or replace the type |

## ORM caveats

- An ORM model that still declares a dropped column will select it and fail.
  Remove the attribute (or mark it deferred) in the release before the
  contract migration.
- An ORM model that declares a new non-null column will insert without it in old
  versions; keep the column nullable or defaulted until every writer sets it.
- Autogenerated migrations do not know about phases. Review every autogenerate
  output and split it into expand and contract revisions.

## When downtime is acceptable

Small internal tools, empty tables, or announced maintenance windows may not
need every phase. Record the decision in the revision docstring and in the
[migration checklist](../assets/migration-checklist.md.template), and still
measure lock duration in a production-like environment.
